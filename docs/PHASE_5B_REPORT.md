# Phase 5B: GCash customer payment sandbox

GCash is now the selected customer method in the storefront and order library, using a sandbox-only PayMongo hosted-checkout adapter. Added verified-email gating, immutable server-priced orders, safe hosted links, one persisted checkout session per order, authenticated resume/status checks, raw-body HMAC signature verification, canonical checkout/payment verification, atomic idempotent fulfillment, conflict detection, admin reconciliation and confirmed-refund access revocation. Refunded orders remain terminal and payment retries cannot restore manual revocations.

Primary changes: src/lib/paymongo.ts, gcash.ts and payment-policy.ts; customer/admin payment routes and webhook handler; storefront/purchase/admin screens; production access guards in commerce/exams/mail; migrations 202610200006_gcash_sandbox and 202610200007_gcash_intent_binding; provider protocol unit tests, disposable payment emulator and desktop/mobile GCash tests. All previous migration checksums were preserved; the intent binding was added separately.

Verification completed locally: lint, TypeScript, 24 unit tests, draft-content validation, database integration and production build. The two GCash browser/security tests passed against a local protocol emulator on desktop and mobile, including actual intercepted hosted-page navigation, canonical amount/mode rejection, unverified/foreign-user denial, repeated checkout/payment events, conflicting event bodies, late/refunded events, revocation preservation and ambiguous creation recovery. Existing production and development regressions are also run before finalizing this milestone. No real funds moved, no real provider credentials were used, and no actual content/products/templates were approved or activated. Protocol fixtures do not establish merchant sandbox compatibility.

The official PayMongo Node SDK was inspected for authentication/payment/refund/signature behavior. Its Checkout Session API is absent. Current Checkout API documentation/API access is blocked by cloud networking; domain additions were saved for user review but not applied/published. Checkout request/response assumptions must be confirmed against the current reference and an actual merchant account before enabling real sandbox use. See GCASH_OPERATIONS.md for exact evidence boundaries and setup.

Still required: merchant account with GCash activation; secure test API key and webhook signing secret; current provider contract verification; actual HTTPS sandbox callback tests covering success/failure/cancel/replay/refund; and sanitized provider evidence. Live keys/events/mode and production checkout remain unconditionally disabled, and paymongo_test records cannot grant production downloads/exams/mail. This milestone observes provider refunds; it does not initiate a funds-moving refund API. Any positive confirmed refund conservatively revokes the whole bundle, including partial refunds; production partial-refund accounting needs separate review.

Actual curriculum/source review, the 500-question human review target, real mail authorization, durable storage/backup/restore, public support/legal policies and remaining launch hardening are also unfinished. Local code commits have not been pushed or verified in a fresh restored cloud task. No live GCash integration or commercial readiness is claimed.

Final regression evidence: 24/24 unit tests; 2/2 local GCash desktop/mobile tests; 14/14 production browser/security tests with test configuration present; and 4/4 development recovery/mock-commerce tests passed. Lint, TypeScript, content/database checks and the production build passed. Repeated migration deployment had no pending changes, and all seven recorded migration checksums matched their files. The mobile GCash storefront screenshot was visually inspected. Cloud start instructions, safe disabled-by-default PayMongo variable requirements and the two required domain additions were saved for review; saving did not apply runtime changes or publish the environment.
