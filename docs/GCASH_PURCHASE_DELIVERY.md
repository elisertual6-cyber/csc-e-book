# GCash payment and reviewer email

This is the current implementation reference. The earlier sandbox protocol remains documented in GCASH_OPERATIONS.md. The operator requested GCash payment followed by an email link to the reviewer. The implemented path is: signed-in verified buyer → server-priced released PDF edition → PayMongo-hosted GCash checkout → verified provider confirmation → paid order/entitlement/unique notice → encrypted purchase email → signed-in library → freshly issued private PDF download. The existing online guides and five free sets remain free.

## Current release state

**Real payments remain off by default and have not been activated or verified with a merchant.** No provider credentials, merchant account approval, live transaction, reviewed commercial PDF release or real purchase-email receipt was supplied/observed during this task. The official Checkout reference request returned HTTP 403 in this environment. The existing canonical API contract is tested against the local emulator, not certified against today's provider service. Validate the current official PayMongo Checkout/webhook contract and an actual merchant sandbox before enabling real sales. No funds were transferred and no external purchase emails were sent by the automated tests.

The adapter now has an explicit live mode. It requires **all** of PAYMENT_PROVIDER=paymongo, PAYMONGO_MODE=live, GCASH_CHECKOUT_ENABLED=true, GCASH_LIVE_ENABLED=true, production runtime, an HTTPS non-loopback APP_URL, a matching server-only `sk_live_` key and the live webhook signing secret. Test mode remains rejected in production. Live mode rejects emulator overrides, test API keys, test resources/events/signature slots and mismatched refunds. Persisted checkout-begin audit records bind each session to its original mode; switching deployment modes cannot resume or fulfill an old checkout as a different kind of payment. Ambiguous creation still requires reconciliation; remote POST creation is never blindly retried.

Live order/checkout creation also requires PURCHASE_MAIL_AUTOMATION=true and valid SMTP/mail-encryption configuration. Payment confirmation itself does not depend on SMTP availability: confirmed payments remain committed and their notices can be recovered later. Existing mock/sandbox records and DRAFT proof artifacts remain forbidden for production email/downloads/exam access. A real sale still requires the existing released FULL PDF, matching version/hash and at least 500 independently reviewed published questions. This implementation does not create approvals, fabricate merchant evidence, activate products or bypass release checks.

Turning off checkout/live-sales flags pauses new charges but still permits authenticated canonical confirmation/refunds for existing same-mode sessions while their mode, credentials and HTTPS origin remain configured. Confirmation-only clients cannot make remote checkout POSTs. Keep webhook/API credentials and the matching payment mode available while reconciling outstanding orders; removing them blocks verification and requires operator recovery.

## Purchase email behavior

Set PURCHASE_MAIL_AUTOMATION=true in Vercel Production only during the reviewed rollout, reusing the same already configured strict-TLS SMTP settings and existing MAIL_ENCRYPTION_KEY. After a paid webhook, owned payment-status refresh or admin reconciliation commits, Next after-response work queues/dispatches **that order's purchase message only**. Unpaid/refunded/ignored/duplicate-unbound outcomes do not trigger a queue sweep. No internal message/recipient/token is exposed in API responses or logs.

The unique delivery notice and unique encrypted mail record prevent extra queue entries from concurrent confirmations. Delivery retains the existing two-minute leases, SKIP LOCKED claims, bounded exponential retries, five-attempt terminal cleanup and payload erasure after acceptance/cancellation. SMTP is at least once: an acceptance followed by a process failure can produce a duplicate. Every dispatch rechecks verified recipient, paid order, coherent amount/currency/items, matching current entitlements and runtime-allowed payment provider. Refunded, revoked, expired, malformed, orphaned or unverified purchases are cancelled. Account verification/reset/password-change messages are excluded from purchase claims, and the account retry worker still excludes purchases.

Emails name the purchased edition/version and link to `/account/purchases`. They never contain object keys, public Supabase links, passwords or the five-minute single-use download token. A signed-out buyer is directed through `/login?from=library` and then back to their library. Only that exact fixed `from` value affects the destination; arbitrary return URLs are not accepted. On opening the library the buyer requests a fresh owner-bound private link, which rechecks payment/content/access and file integrity. Refund/revocation still blocks download even if an old email is retained. Provider SMTP acceptance is not proof of Inbox placement.

## Retry job and secure setup

The new **Retry paid reviewer email** main-only workflow is gated by repository **Variable** PURCHASE_MAIL_AUTOMATION=true. It reuses existing database/CA/SMTP/mail-key **Secrets** and requires no new mail provider. It materializes at most ten purchase notices and claims at most ten due purchase messages, including expired leases; it never processes account mail. The five-minute GitHub schedule is best effort and may be delayed/disabled, so it is not an immediate delivery guarantee. A failed request callback leaves the committed notice available to this sweep. Keep the Vercel flag off and the GitHub variable unset/false until rollout is ready; disabling either does not regenerate or erase encryption keys.

Before enabling a merchant, supply its status and choose the paid reviewer format. For the implemented downloadable edition, prepare and independently release the eligible PDF/product and PHP price. Verify a real merchant sandbox using an isolated HTTPS test deployment and provider-documented GCash test flow, then configure live secrets securely in Vercel (never in chat, NEXT_PUBLIC variables, Git or workflow inputs). Register `/api/commerce/webhook` for the documented payment/refund event types with the corresponding live signing secret. Keep PAYMONGO_TEST_API_ORIGIN unset. Verify actual successful/cancelled/delayed/duplicate/wrong-amount/refund events, private owner-only delivery and received email before a customer launch. Authentic refund initiation remains a merchant-dashboard operation; the app observes verified refunds and revokes access.

`npm run payments:check` validates configuration only and prints field names/fixed categories, never credential values. It makes no provider call, sends no email and does not certify merchant approval, current provider compatibility, commercial content or mailbox delivery. The purchase retry CLI is `npm run mail:purchase:work -- --send`; it also requires the purchase automation flag and secure mail/database settings.

## Verification

Use only disposable wrappers: test:gcash for canonical payment/refund/idempotency plus automatic private test-inbox delivery; test:mail:purchase for real loopback SMTP, scoped concurrency/retry, account-message exclusion, cancellation and production sandbox denial; test:mail:automatic for existing account recovery; test:commerce for existing private download/access checks. Run the required lint/type/unit/content/database/build, browser and signed-in accessibility checks. Tests use synthetic identities/payments/reviews, private temporary files and a local provider emulator; they are not human content approval or actual merchant/live-money evidence.
