# Architecture

Current operational boundary: API handlers use a shared error/response wrapper with generated request references and fixed-category private completion/error events. `/api/live` is Node uptime; `/api/health` checks actual database connectivity through a separately bounded one-connection diagnostic pool without changing business transaction limits. Hosted demo availability is distinct from database/provider/content readiness. See OPERATIONS_MONITORING.md for log coverage, privacy and load-test limits.

The Phase 1 boundary is a public educational demo. Next.js App Router renders pages on the server. Tailwind and local CSS provide navy, ivory and gold styling without government marks or external fonts. Only the ungraded arithmetic demo uses client state; it has no assessment answer key or score. Original Markdown lessons live in content/lessons. A typed curriculum index connects common subjects, Professional analytical topics and Subprofessional clerical topics.

PostgreSQL 17 is the system of record. Prisma models identity/roles, editorial versions and reviews, sources, exams/attempts/responses, catalog/prices, orders/payments/entitlements, protected artifacts and audit events. src/lib/db.ts is server-only. The public demo uses local draft data deliberately and never impersonates a logged-in account. /api/health checks connectivity with SELECT 1 and reports 503 without leaking connection errors. A running landing page alone does not establish database readiness.

Future boundaries: Auth.js sessions with secure cookies and role checks on every protected action; Zod-validated inputs; transaction-based order/payment transitions with provider event idempotency; private object keys rather than public paid URLs; short-lived signed downloads issued only after entitlement checks. Attempt creation must choose reviewed questions and persist immutable version snapshots. Server timestamps and a transaction-protected submission determine grades; client clocks are presentation only. Explanations become available only after submission. Add distributed rate limiting before public authenticated endpoints.

PDF generation runs in a Node worker/container with Playwright and installed browser binaries, outside edge runtime. Store preview PDFs publicly and full PDFs in private S3-compatible storage. No provider or storage credentials are needed for Phase 1. Vercel can host the web app with managed PostgreSQL; browser-based PDF work needs a separate worker. Build does not require a database; migrate and seed before health checks.

Current schema constraints cover unique choices/answers, one response per attempt question, unique provider events and order entitlements. Application-level invariants (one correct answer, reviewer authorization, version immutability, valid state transitions, expiration, cross-model ownership and payment verification) need the later service layer and tests before writes are exposed. No authentication, admin API, payment processing or paid file serving is implemented in Phase 1.


## Phase 2 implementation

The compatible authentication implementation uses asynchronous scrypt (N=65536, r=8, p=2; random per-password salt), random 256-bit session tokens, SHA-256 token hashes in PostgreSQL, 24-hour expiry and HttpOnly/SameSite cookies with Secure/__Host- prefix in production. Each protected request reads the current database role. Login uses uniform invalid-credential responses and the same KDF for unknown identities. PostgreSQL fixed-window counters limit auth, imports, editorial writes and PDF rendering. Mutations require a strict configured APP_URL Origin, JSON content and a non-simple action header. No CORS allow policy is emitted. Public registration cannot set roles and defaults off in production. Local CLI role changes revoke sessions. Verification/password reset were subsequently added in Phase 5A; no real SMTP or external identity provider is configured.

Editorial mutations run in transactions and emit audit events. Authors edit only their own DRAFT; reviewers must differ from authors. A content hash binds approval to exact lesson/question fields; admin release revalidates it. Published content is immutable and revisions reject stale writes. Independent approval is a human attestation, not an automatic correctness check. Seed records remain unauthored drafts and need a newly authored version before the workflow can release them.

The Node PDF worker renders selected versions with Playwright/Chromium, without JavaScript, raw HTML/images or browser network access. It stores a generated UUID filename and raw-byte SHA-256 plus an immutable version manifest in PdfEdition, and writes only to a private local-volume adapter. DRAFT and FULL files require staff sessions; a PREVIEW candidate has a separate admin release attestation. Every public preview request rechecks current version eligibility and file integrity. FULL requires 500 unique published, independently reviewed question keys. Customer paid file delivery, object storage and entitlements are still Phase 4 work. PDF routes need a Node container with Chromium and durable storage; Vercel web/edge alone is insufficient.

End-to-end tests use a freshly generated disposable database and private directory, apply all migrations, and destroy only those generated resources afterward. This permits simulated approval/publication tests without contaminating the development bank or exposing fixtures through its public server.


## Phase 3 implementation

ExamTemplate defines PRACTICE/MOCK and FREE/PREMIUM, track, topic scope, count and duration. Templates begin inactive; admin activation checks independently approved PUBLISHED question availability. Starts recheck the bank, select unique latest eligible keys with cryptographic random sampling, and freeze private question/settings JSON plus opaque per-attempt question keys. Shared COMMON content is eligible for either track. Client DTOs explicitly whitelist question text/options and own saved responses, never serializing snapshots or correct flags before submission.

A per-user PostgreSQL advisory transaction lock serializes idempotent starts and the three-active-session quota. UUID start keys bind to exact selection parameters. Attempt row locks serialize reads/writes/finalization; revision numbers reject stale answer batches. Validation precedes writes for atomic failure. The database clock is evaluated after the row lock before accepting a save. Expired payloads are ignored and stored responses graded. Submission is idempotent, has no client answer/score/timestamp payload, and emits one finalization event. Later bank/template versions never change a started attempt. Expiration is finalized on subsequent service reads/writes/history/start cleanup, not by a claimed background scheduler.

Premium attempts recheck an unrevoked/unexpired entitlement, exam-granting product, same-user PAID order, matching product/price line items and totals/currencies, and a matching VERIFIED payment with verifiedAt. Mock provider records do not unlock production customer access. Staff have an explicit QA bypass. Development fulfillment is implemented in Phase 4; real gateway verification remains a blocked production integration. Historical summary scores remain visible to their owner after access loss, but private question details and writes are denied.

The learner UI uses acknowledged server progress, navigation, flags and timer synchronization, and stops edits after unconfirmed/conflicting writes until reload. It stores no questions/answers in localStorage. Results show grading explanations and subject counts only after finalization. History includes all active sessions and recent 50 completions; averages are labelled recent practice values, never CSC scores. UI/API tests simulate review/payment states only in disposable databases, including clock changes, concurrent starts/saves/submissions and revoked access.

## Development commerce boundary

Commerce routes delegate to a server-only service and the mock payment boundary. Per-customer advisory locks serialize idempotent order creation; product locks coordinate activation/pricing, and order row locks serialize payment/cancel/refund/access changes. Immutable item snapshots retain purchased names, versions and amounts. Fulfillment writes verified mock payment, PAID order, unique entitlement, unique development-outbox notice and audit atomically. Real webhooks fail closed.

Artifact metadata maps product versions to checksum-verified private PDF editions; development proof artifacts are explicitly marked and blocked in production. Download grants store only token hashes, enforce owner/expiry/single consumption with row locks and revalidate entitlement/order/payment/content on every request. Private local disk and the database outbox are development implementations; remote object storage, provider email delivery and a real signed payment adapter remain deployment integration work.

## Account security and mail delivery

Phase 5A adds hashed, purpose-bound verification/reset credentials and immutable address/auth-generation binding. User row locks serialize credential issuance/consumption, resets and session creation. Reset increments the authentication generation, revokes sessions and cancels outstanding credentials/mail in one transaction; session reads also compare the generation. Fragment credentials stay out of HTTP requests and only explicit POST confirmation mutates accounts.

MailMessage persists AES-256-GCM encrypted recipient/subject/text. A separate Node worker claims due rows with leases and SKIP LOCKED, rechecks eligibility and submits via private development files or a strict-TLS Nodemailer SMTP adapter. Successful, cancelled, expired and terminal-failure payloads are erased. Stable Message-ID helps deduplication, but SMTP delivery is at least once and acceptance is not guaranteed inbox placement. Purchase notifications require verified email, coherent paid state and live entitlements. See ACCOUNT_SECURITY.md for configuration, retries, scheduling and remaining provider authorization.

## GCash sandbox boundary

PaymentSession binds one order to one local/remote PayMongo checkout and intent; CREATING is persisted before a single external POST, with ambiguous results requiring reconciliation. Signed webhooks and owned status checks retrieve canonical resources, validate exact server order metadata/method/line totals/mode and serialize fulfillment under order/event locks. Payment IDs, event receipts, entitlements and notices prevent duplicate grants. Confirmed refunds revoke access and are terminal; retries never clear manual revocations. Sandbox payments are marked paymongo_test and blocked from production downloads/exams/mail. The API-origin override/emulator is restricted to generated disposable test databases. Current provider Checkout API compatibility and merchant sandbox evidence remain external release prerequisites; production checkout is unconditionally disabled.
