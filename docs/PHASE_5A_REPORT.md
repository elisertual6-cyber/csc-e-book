# Phase 5A: account security and transactional mail

Implemented email verification and password recovery with explicit confirmation screens, expiring single-use hashed credentials, role/address/purpose/auth-generation binding, uniform account-request responses, strict mutation checks and rate limits. Password reset uses a locked-user transaction to revoke all sessions, increment the authentication generation and cancel old credentials/messages. Login/session creation checks the same generation under the same lock to prevent stale-password races. Operator role changes invalidate generations too.

Added an AES-256-GCM encrypted mail queue, private development file inbox, Node SMTP submission adapter and one-batch operator worker with row claims, leases, retry/backoff, stable Message-ID and payload erasure. SMTP requires TLS/certificate verification; plaintext is restricted to loopback development receivers. Purchase notices require a verified address, coherent paid state and current purchased entitlements. They link to the authenticated account rather than embedding premium files/download credentials. Added expiry maintenance, configuration guidance and honest notification status copy.

Primary changes: Prisma migration 202610200005_account_security_mail; src/lib/account-security.ts, mail.ts and auth.ts; auth route handlers; verification/recovery/account screens; scripts/mail-worker.ts and maintenance/role scripts; mail unit tests and isolated recovery/SMTP browser tests. See ACCOUNT_SECURITY.md for complete semantics and setup.

Validation: lint, TypeScript, 19 unit tests, content validation, database integration, repeatable migration deployment and a production build. Browser suites exercise desktop/mobile recovery, verification, expiry, supersession/replay/wrong-purpose rejection, concurrent reset/login behavior, revocation, queue claims, actual local SMTP acceptance/rejection/retries, purchase-notice deduplication and existing commerce/exam/editorial regressions. Test mail is confined to private directories and loopback test receivers; no real recipient receives it. Production dependency audit reported zero vulnerabilities on 20 October 2026. Detailed final test counts are recorded after completion below.

The operator-provided email was saved only in ignored private local settings as operator/proposed sender metadata. No account password, Gmail authorization or actual SMTP provider was supplied. Sending from an address is not enabled merely by providing that address. Production mail defaults disabled, file transport is forbidden there, and production checkout is still disabled. A provider must be authorized through secure environment settings and tested for real delivery/bounces before public rollout.

Remaining: independently reviewed curriculum and 500-question bank, authoritative source verification, real gateway signatures/sandbox/refunds, durable private storage, backup/restore proof, production mail authorization/scheduling/monitoring, accessibility/load/security/observability checks and final monitored public support/legal policies. Existing login/practice remain available without mandatory verification; a future commercial checkout must explicitly enforce its verified-email policy. No real editorial content or products were auto-approved/activated. This milestone does not complete the entire product or certify launch readiness.

Final regression evidence: 19/19 unit tests, 14/14 production browser/security tests and 4/4 combined development recovery/commerce browser tests passed. The final worker purpose-binding guard was additionally tested on both desktop and mobile. The ordinary development mail worker completed with zero pending messages and no external send. Production build, content/database checks, maintenance and repeat migration deployment passed. Private local settings were preserved and no secrets or real account mail entered Git.
